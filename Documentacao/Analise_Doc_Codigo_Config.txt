PARTE 2 - FLUXO DE CONFIGURACAO DINAMICA
====================================================================

OBJETIVO

Descobrir em que ponto o app respeita a configuracao dinamica do cliente e em que ponto deixa de respeitar.


FLUXO ESPERADO

1. O usuario informa o identificador da configuracao.
2. O app busca no backend os enderecos do cliente.
3. O app salva no store:
   - urlLogin
   - urlAPISuprimentos
   - urlAPISP7
4. Todos os servicos deveriam consumir essas URLs dinamicas.


ONDE O FLUXO ESTA CORRETO

1. O componente de configuracao chama LoginService.getConfig().
2. O LoginService salva as URLs dinamicas no store.
3. O AuthState monta urlAPISuprimentos + '/api' e urlAPISP7 + '/api'.
4. Os servicos antigos usam essas URLs dinamicas corretamente.

Exemplos de modulos que respeitam o store dinamico:
- RequestService
- LoockupstService
- DocumentService
- InsumosRequest
- InsumosRequest Frota
- UpdateRequestStatus


ONDE O FLUXO QUEBRA

1. A busca inicial de configuracao usa uma base fixa de environment.
   Resultado:
   - O primeiro passo ja depende de uma URL hardcoded.

2. Existe um ApiService novo que usa base fixa do environment.apiUrl.
   Resultado:
   - Os servicos novos que dependem dele ignoram o store dinamico.

ATUALIZACAO EM 17/04/2026

- Este ponto foi corrigido no codigo atual.
- O arquivo src/app/services/api.service.ts agora consulta primeiro AuthUser.geturlAPISP7 no store e so usa environment.apiUrl como fallback.
- Com isso, os modulos novos que dependem de ApiService passaram a respeitar a URL dinamica apos a configuracao ser carregada.
- A pendencia restante desta frente continua sendo a busca inicial de configuracao em LoginService.getConfig(), que ainda chama environment.BASE_URL.

3. Os modulos novos afetados por essa base fixa incluem:
   - AbastecimentoService
   - OrdemServicoService
   - InsumoService
   - EtapaService

ATUALIZACAO EM 17/04/2026

- Como o ApiService foi ajustado para usar o store dinamico, esta lista deixa de estar afetada por base fixa dentro do proprio ApiService.
- Ainda assim, esses modulos continuam dependendo de a configuracao inicial ter sido carregada corretamente antes do uso.


CONCLUSAO DA PARTE 2

O projeto esta misturado.

Parte antiga:
- Usa a configuracao dinamica do cliente corretamente.

Parte nova, principalmente frotas:
- Usava ApiService com base fixa do environment.
- Isso podia forcar chamadas para a base demo ou para uma base errada.

ATUALIZACAO EM 17/04/2026

- O ApiService foi corrigido e agora usa a URL dinamica do store.
- O risco remanescente de base fixa ficou concentrado no fluxo inicial de descoberta de configuracao em LoginService.getConfig().

PARTE 3 - ERRO FIREBIRD
====================================================================

ERRO RECEBIDO

Mensagem principal:
- Erro ao conectar na base de dados do Firebird. Verifique o log!

Mensagem detalhada importante:
- Your user name and password are not defined. Ask your database administrator to set up a Firebird login.


INTERPRETACAO TECNICA

Esse erro indica:
1. O frontend conseguiu chamar a API.
2. A API entrou no backend e tentou consultar a base Firebird.
3. A conexao com o Firebird falhou por credencial ausente, invalida ou configuracao errada no servidor.

Ou seja:
- Nao e um erro de rota inexistente no app.
- Nao e um erro de parsing do frontend.
- E um erro de backend e/ou configuracao da base do cliente.


ONDE ISSO APARECE NO APP

O erro menciona PesquisaRequisicoes.

No app, esse fluxo passa por:
- RequestService.getReq()
- EnumRequest.PesquisaRequisicoes = /suprimentos/Requisicao/PesquisaRequisicoes

Importante:
- Esse fluxo de requisicoes usa URL dinamica vinda do store.
- Portanto, isoladamente, esse erro parece muito mais um problema do ambiente/backend do cliente do que do modulo de configuracao fixa da parte de frotas.


CENARIOS PROVAVEIS PARA ESSE ERRO

Cenario A - Backend do cliente com Firebird mal configurado
- Mais provavel para o fluxo de requisicoes.
- A API certa foi chamada, mas o servidor nao conseguiu autenticar no Firebird.

Cenario B - O app foi direcionado para ambiente diferente do esperado
- Possivel principalmente nos modulos novos de frotas/abastecimento/os.
- Menos provavel para o fluxo de requisicoes, porque ali o app usa a URL dinamica corretamente.


CONCLUSAO DA PARTE 3

Para esse erro especifico de Firebird:
- O indico principal e backend/configuracao do servidor de banco.
- Nao ha evidencia forte de que esse erro tenha sido gerado por rota incorreta no frontend de requisicoes.
